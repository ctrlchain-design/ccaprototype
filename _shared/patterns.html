Top bar — trailing cluster

Contact Support, notifications, language switch with flag, user menu. Do not copy this markup. It is shared, in _shared/shell-markup.js, and a prototype gets it by putting <div data-top-bar-trailing> in its header — the demo to the right is that module rendering itself. One definition is the point: a copy per prototype is how two of them end up disagreeing about what the product’s chrome looks like. Staging is not a reliable reference for this bar — it shows no Contact Support link and no flag, but production has both. Contact Support is cca-btn--tertiary, the app’s own class, not cca-btn--link, which hard-codes an underline. The avatar is initials using the avatar tokens — the app shows the signed-in user’s photo, which a shared prototype should not carry.

Saved-view tabs

160×48 per tab, 1px neutral bottom border, 2px brand border on the active one, plus a flexing filler so the border reaches the edge. These are not Material tabs — a saved view carries an icon and a kebab menu, so it is its own component. Use mat-tab-group for a plain tab strip, not for these.

Do not render the row when "All" is the only view. One tab is not a choice, and the app agrees: Contracted Lanes has no saved views and shows the toolbar straight away with no tab row, even though its URL still carries viewId=all. Orders, which has views, shows "All" plus them. Drop the filler too, or an empty rule hangs under the toolbar with nothing above it.

The kebab on the active tab is Set as Default / Rename / Delete — it manages the view you are on and does not create one. Rename and Delete are disabled on "All", which is a system view.

This note used to say Material tabs were unusable in a static page because the indicator needs Angular to size it. That was the wrong diagnosis. The indicator is sized in CSS — it is position: absolute inside the tab — and the export is simply missing .mdc-tab { position: relative }, so it resolved against the whole strip and drew one green line across every tab. prototype.css restores the rule, and legal/admin uses a real mat-tab-group with no Angular at all. The design system's own components/tabs.html still shows the broken version — worth reporting to FE.

Pinned filter chip

A pin glyph and a filter name. Figma draws it at a 10px radius, which has no utility in the scale (4 / 6 / 8 / 12 / 16), so it uses rounded-lg. The background is surface-neutral-dark — counter-intuitively named, but it is #ebebeb in light mode and inverts correctly, which a raw hex would not.

The glyph is pinned-yes, not pinned. Plain pinned is the UNPINNED state — an outline. This pattern showed the wrong one until 2 Sept 2026, so anything copied from it before then has an unpinned pin on a pinned chip. The pair is pinned-yes / pinned, as the running app uses them.

The second chip is the applied form: the name, a colon, the values, and an ✕ that clears the values but leaves the pin. These are clickable — the app opens the filter's values in a checkbox popover from the chip, so the common case never needs the drawer. Do not rebuild any of that: _shared/filters.js has the whole mechanism, and the app renders this chip with its own cca-filter-values-chip component (ds/components/filter-values-chip.css) if you need to go closer.

Badges — flavour names lie

On cca-numerical-badge, .primary is red. Green is .success; white-on-green is .inverted. Flavour sets also differ per badge component. Read the component's stylesheet in design-system/dist/ds/components/ rather than trusting a name, and if a Figma layer names a token, grep for that token instead. Sizes are not modifiers either — they come from the type and padding utilities on the inner div.

Rail: Dark and Collapse

Both are wired by _shared/shell.js — include it once and tag the rail rows with data-theme-toggle and data-submenu-toggle. Both mechanisms are the platform's: theming is a dark class on the root element (which :root.dark uses to redefine all 492 tokens, the same way the exported catalogue's own toggle works), and collapse is smallSideNav on cca-main plus hidden on cca-side-submenu. Note the naming: smallSideNav is the expanded state — the submenu column is 0 without it.

No demo here — it needs the rail. Open any prototype and use the two items at the bottom of the sidebar.

File upload dropzone

The platform's cca-file-upload, read off an order's Documents tab. Composed from utilities — there is no dropzone stylesheet in the export, so the classes on the box are the component.

The dashed border has no colour class. The app writes border-neutral-dark-700, which is not in the design system and resolves to nothing; the colour comes from currentColor via text-neutral-title, which is why it computes to #3e3e3e and still inverts in dark mode. The dead class is left out here. If you want it stated, border-neutral-darker is the token that equals it.

Make the box a <label> around a hidden <input type="file">: "browse" then opens the real picker with no JavaScript. Drag-and-drop needs dragover cancelled or the browser opens the file instead of handing it over — and a dropped file never lands in input.files, so hold it in a variable rather than reading the input back.

One file only? Leaving multiple off the input covers the picker, but not a drop — that is the one route more than one file can arrive by. Taking files[0] and discarding the rest silently is the wrong answer: the person sees their other files vanish unexplained. Check files.length, say so, and take none.

Re-upload rather than edit. There is nothing to edit in a PDF, so the same dialog does three jobs, and which one it does depends on the version's status. Legal's rule: an edit goes a point up (2.2 → 2.3), a new version goes a whole up (2.2 → 3.0). But a version nobody has been held to has nothing to supersede, so editing a draft replaces its file and leaves the number alone. Only a published version is ever left untouched with a correction beside it — which is what lets terms someone accepted be produced later. See nextVersionNumber() and replaceFileOnVersion() in legal/admin-document/document.js.

One format only? Same shape of problem. accept greys out other types in the picker but is only a filter — the picker's own "All files" option switches it off — and a drop goes through neither accept nor multiple. Validate in the change handler AND the drop handler.

On dragover the browser exposes each item's type but not its name, so decide with the type alone, set e.dataTransfer.dropEffect = 'none' to turn the cursor into "no drop", and paint the zone as refusing — critical-border + critical-surface-lighter. Then check again on drop, where the filename finally exists. Show the refusal where the file would have appeared, not in a snackbar that slides away before they try again.

The glyph is the platform's own and the export omits it, so it lives in _shared/assets/images/ beside the flags.

Reader-facing legal pages

Recorded so it is not rediscovered, and corrected after checking development: these are pages, not modals. The account menu links to /privacy-policy/<id> (tabs across the top, one per region — EU, USA) and /terms-of-service (no tabs, there is only one document). Both show an "Updated at" line and then the document.

Neither has a submenu. The shell is rail + header + banner + page, and the content runs the full width — worth knowing, because every prototype in this repo so far has a submenu and the starter template ships one.

A reader sees the live version only — no version dropdown, no Edit, no Publish. What the body holds depends on how that version was made: rich text if written, the PDF if uploaded. That fork already exists in versionBodyHtml() in legal/admin-document/document.js; a reader page is those two branches with the admin controls stripped off.

Built now — legal/privacy and legal/terms. Uploads made on the admin screen are kept in localStorage by _shared/legal-store.js so they survive the navigation to these pages, which a blob URL would not. That storage is per browser: one person can walk the whole journey, two people cannot share it.

The screen names are already claimed — legal.privacy and legal.terms, linked from the account menu in _shared/shell-markup.js — so they explain themselves today and start working the day the pages land.

No demo — nothing is built. Open the account menu in any prototype to see the links, and legal/admin-document for both content branches as they render today.

Action chooser dialog

The app's "Select" dialog — one card per way of doing a thing. Read off Orders › Actions; also used by Legal to ask whether a new version is uploaded or typed. Header with a title and an X, then cca-card-buttons in a flex flex-col gap-4.

.dialog-container and its header / main / footer are fully styled by platform-02.css, so use those element tags — the padding, the divider and the close button all hang off them. cca-card-button itself carries no styling: the utilities on its inner div.card-button are what you must copy, and the custom element needs an explicit display like every other one.

It is a dialog, so the scrim is cdk-overlay-dark-backdrop at 0.32 — not the drawer's 0.6. Two states start invisible and are released together by mdc-dialog--open on the container: .mat-mdc-dialog-inner-container at opacity 0 and .mat-mdc-dialog-surface at scale(0.8). Add that class after a layout read, never in a requestAnimationFrame. Centring is .proto-dialog-wrapper; width belongs on the pane (the action chooser is 45rem).
